# UI guidelines

## 1. Purpose and assumptions

This spec owns the visual language of the demo: aesthetic direction, design tokens, typography, component rules, layout, status colour, motion, and accessibility. It applies to every route in [architecture.md](./architecture.md) §5. Behaviour and access rules live in the other specs; this document only says how things look and feel.

Assumptions:

- Stack is Tailwind CSS v4 + shadcn (`base-nova` style, `neutral` base colour, CSS variables on) + lucide icons, loaded through `src/app/globals.css` and `components.json`.
- Fonts are loaded with `next/font` in `src/app/layout.tsx` (Geist, Geist Mono) and exposed as `--font-geist-sans` / `--font-geist-mono`.
- The reference aesthetic is Linear and Cursor: quiet, dense, monochrome-first, with colour reserved for meaning.

## 2. Aesthetic direction

The product should read as a serious internal tool, not a marketing site.

- D1. **Monochrome first.** Surfaces, text, and borders use the neutral scale only. Hue appears for exactly three reasons: a person status or an overdue or at-risk signal, a validation outcome, or a focused control. Charts are the one bounded addition: two or three hues per chart from the chart tokens (§5.8 CH2).
- D2. **Hierarchy through weight and tone, not size.** Prefer `font-medium` + `text-foreground` versus `text-muted-foreground` over jumping type sizes. Page titles are `text-2xl`; everything else is `text-sm` or `text-base`.
- D3. **Borders over shadows.** 1px `border-border` separators and `bg-card` panels. No drop shadows except on popovers and dialogs (`shadow-md` max).
- D4. **Dense but breathable.** Default vertical rhythm is 4/8/12/16/24 px (`gap-1` … `gap-6`). Tables and lists use `py-2`–`py-3` rows. Nothing wider than `max-w-5xl` for content; forms cap at `max-w-md`.
- D5. **Restrained radius.** `--radius` is `0.625rem`; use `rounded-lg` for panels and buttons, `rounded-md` for inputs and badges, `rounded-full` only for avatars and dots.
- D6. **Quiet motion.** Transitions are 150 ms, `ease-out`, on `color`, `background-color`, `border-color`, `opacity`, `transform` only. No entrance animations on page load. Hover states shift tone by one step (`hover:bg-muted`), never scale content.
- D7. **No decoration.** No gradients, no illustration, no emoji, the persona picker included.

## 3. Design tokens

All colour, radius, and font decisions flow through CSS variables defined in `src/app/globals.css` and mapped into Tailwind by the `@theme inline` block. Components reference Tailwind utilities that resolve to those variables; nothing references a palette colour directly.

### 3.1 Token families

| Family | Tokens (Tailwind utility ⇐ CSS variable) | Use |
| --- | --- | --- |
| Surface | `bg-background`, `bg-card`, `bg-popover`, `bg-muted`, `bg-secondary`, `bg-accent` | Page, panel, overlay, inset, subdued fill |
| Text | `text-foreground`, `text-muted-foreground`, `text-card-foreground`, `text-primary-foreground` | Body, secondary, text on surfaces/primary |
| Interactive | `bg-primary`, `text-primary`, `border-input`, `ring-ring` | Primary action, links, inputs, focus |
| Feedback | `text-destructive`, `bg-destructive/10` | Validation and domain errors |
| Signing (added by the signing slice) | `--signing`, `--signing-foreground` | The yellow signature tags and Start/Next button of `SigningDialog`; always dark-on-yellow because the tags sit on a white PDF page in both themes |
| Status (added by this spec, §6) | `--status-neutral`, `--status-info`, `--status-warning`, `--status-success`, `--status-danger` + `-foreground` pairs | Person status badges, overdue and at-risk signals only |
| Chart (§5.8) | `--chart-brand`, `--chart-brand-soft`, `--chart-positive`, `--chart-neutral`, `--chart-caution`, `--chart-alert`, `--chart-critical`, `--chart-pending`, `--chart-hatch` (`bg-chart-*`, `fill="var(--chart-*)"`) | Chart marks only. Derived from `--primary`, `--muted*`, `--card` and the status foregrounds, so a preset restyles them |
| Shape | `rounded-sm` … `rounded-xl` ⇐ `--radius` scale | Corners |
| Type | `font-sans`, `font-mono`, `font-heading` ⇐ `--font-geist-sans`, `--font-geist-mono` | §4 |

### 3.2 Rules

- T1. Components MUST use semantic token utilities (`bg-card`, `text-muted-foreground`, `border-border`). Raw palette utilities (`bg-zinc-950`, `text-sky-700`, `#hex`, `oklch(...)` in JSX) are forbidden outside `globals.css`.
- T2. New tokens are added in `globals.css` in both `:root` and `.dark`, then mapped in `@theme inline`. A token that exists in only one theme is a bug. Derived tokens (the chart family) are the exception: they are written once as `color-mix` / `var()` of other tokens on `:root, .dark, [data-theme]`, so they re-resolve wherever a theme or preset redefines their sources; a dark-only adjustment goes in a `.dark, .dark[data-theme]` block after it.
- T3. Theming is done by changing variable values, never by changing component classes. Presets are defined once in `src/lib/themes.ts` (`THEME_VARS`, `THEMES`) and emitted by the root layout as one `[data-theme="<id>"]` rule per preset; a preset only restyles the §3.3 variables. Status tokens are shared across presets.
- T4. Opacity modifiers on tokens (`bg-primary/80`, `ring-ring/50`) are allowed; they keep the colour tied to the token.
- T5. Pages MUST NOT define CSS. Styling lives in Tailwind utilities in JSX, `cva` variants in `src/components/ui`, and `globals.css`. No CSS modules, `<style>`, or inline `style={}` for anything a utility can express. Sole exceptions: the generated theme stylesheet in the root layout, and colour swatches whose value is data (`style={{ backgroundColor }}`).
- T6. `src/app/pick/page.tsx` renders inside `ThemeRoot` like a portal (the user's preset, L5) and uses tokens only; the avatar role dots are the §6 status tokens (S3).

### 3.3 Presets and application

| Preset id | Role |
| --- | --- |
| `monochrome` | Default. Near-black primary, neutral surfaces (Linear/Cursor direction) |
| `classic` | Blue primary, faint cool tint — the eor-prototype default |
| `dark` | Dark surfaces; also sets the `dark` class so `dark:` utilities apply |
| `warm`, `ocean`, `forest`, `violet` | Accent variants; faint hue tint on surfaces |

- P1. The active preset is applied server-side by `ThemeRoot` (`data-theme` on the portal wrapper), read from the `eor_theme` cookie with `monochrome` as fallback. No client-side variable injection: the first paint is already themed.
- P2. Preview (Appearance page) flips `data-theme` client-side instantly; Apply persists through a Server Action. A later slice MAY persist per client company and fall back to the cookie.
- P3. A preset defines exactly `THEME_VARS` (surfaces, text, primary, muted, accent, border, input, ring, radius). It MUST NOT redefine status tokens.

## 4. Typography

| Role | Utility | Face | Notes |
| --- | --- | --- | --- |
| Body, UI | `font-sans` | Geist | Default on `<html>` |
| Headings | `font-heading` (= sans) | Geist | Same face; weight does the work |
| Identifiers | `font-mono` | Geist Mono | Case ids, task keys (`verify_i9_section2`), state codes (`CA`), error codes |

- F1. Exactly two faces: Geist and Geist Mono. No third font.
- F2. Scale: `text-xs` (12) captions and mono literals · `text-sm` (14) default UI and table cells · `text-base` (16) long-form only · `text-lg` (18) section headings · `text-2xl` (24) page title. Nothing larger, the persona picker included.
- F3. Weights: `font-normal` body, `font-medium` labels/headings/buttons, `font-semibold` page title. No `font-bold`.
- F4. Numbers that align in columns (wage, markup, fee, dates) use `tabular-nums`.
- F5. Letter-spacing: `tracking-tight` on titles ≥ `text-2xl` and on the "Northwind" name beside the logo; no uppercase eyebrow labels.
- F1a. Exception to F1, scoped to the typed-signature preview: Dancing Script (`assets/fonts/DancingScript.ttf`, SIL OFL) loaded with `next/font/local` in `src/components/signing/signature-font.ts`. It renders only a person's typed name as their signature (the signed tags and the "Adopt your signature" preview in `SigningDialog`, `SignatureSummary`) and matches what is stamped into the PDF. It is never used for UI text.

## 5. Components

- C1. Primitives come from shadcn into `src/components/ui/` via `pnpm dlx shadcn@latest add <name>`; they are then owned by the repo and edited in place. Allowed set for this demo: `button`, `badge`, `card`, `input`, `label`, `select`, `textarea`, `table`, `separator`, `alert`, `dialog`, `tooltip`, `skeleton`, `popover`, `dropdown-menu`, plus `option-select`, `date-picker`, `calendar` (see C9), and `chart` (§5.8, on Recharts). `popover` (Base UI Popover) holds secondary filters behind one button (C30); `dropdown-menu` (Base UI Menu) is an overflow "More actions" menu of commands, never navigation, its items styled like select items with a `destructive` variant.
- C2. Shared app components live in `src/components/`: `portal-shell`, `persona-switcher`, `persona-picker`, `persona-tile`, `employee-search-dialog`, `employee-picker`, `person-status`, `case-timeline`, `onboarding-timeline` (detailed task list), `onboarding-stages` (the stage stepper, C25), `at-risk-flag`, `document-list`, `field-error`, `empty-state`. If two portals need the same visual element, it goes here, not in both pages.
- C3. Variants are declared with `cva`, never by string-concatenating classes in pages. A page may add layout classes (`className="mt-4"`) but not restyle a primitive.
- C4. Buttons: one `variant="default"` per view (the primary action). Secondary actions are `outline`; tertiary and inline are `ghost`; destructive domain actions (reject) are `destructive` (tinted); the solid `danger` variant is reserved for the confirm step inside a dialog. Heights follow the eor-prototype: `default` is `h-10` with `px-4` (page-header actions, forms, dialogs), `sm` is `h-8` (dense toolbars only), `lg` is `h-11`. Focus rings use `focus-visible:` only.
- C5. Forms: `Label` above `Input`, `gap-1.5` between them, `gap-4` between fields. Help text is `text-xs text-muted-foreground`. Errors render in `field-error` directly under the field as `text-xs text-destructive`, using the `ActionResult.message` from [acl.md](./acl.md) §6. Submit button sits left-aligned at the bottom; no centred buttons.
- C6. Tables: header row on its own `bg-muted/60` band so it never reads as a body row, text `text-xs font-medium uppercase tracking-wide text-muted-foreground`; sortable columns use `SortableHead` (button, `aria-sort`, chevron only on the active column, none → asc → desc → none); body `text-sm`, row dividers `border-b border-border`, hover `hover:bg-muted/50`, no zebra striping. A table is for records looked up and compared across columns; a queue of things to act on is a C43 dense list instead (C30).
- C7. Empty states: one line of `text-sm text-muted-foreground` plus, when a valid next action exists, one `outline` button. No illustrations.
- C9. Fields follow the eor-prototype: a filled surface (`bg-muted`), `h-10`, `rounded-lg`, a darker border on hover and `border-primary` plus a ring on focus; required labels end in ` *`. Dropdowns are `OptionSelect`: a themed select that adds a search box above 5 options (the 51-location list included), with the highlighted row tinted `bg-primary/10` and the selected row `bg-muted`. Every popup opens below the trigger without covering it, matches the trigger width, flips above when there is no room, and never leaves the viewport (`selectPopupClass` / `selectItemClass` in `ui/select.tsx` are the single source for the surface and rows). Popups portal to `<body>`, so `ThemeScope` mirrors the active theme onto it; without that they would render in the default theme. Dates use `DatePicker` over the `Calendar` primitive, styled from tokens with no vendor stylesheet (submits `YYYY-MM-DD`); the native date input is not used.
- C10. Creating a related record never leaves the workflow: it opens a dialog and returns the new record to the form (e.g. "New role" on Start a hire selects and prefills the new role). Dialogs use `p-6`; a destructive confirm uses the solid `danger` button.
- C11. Lists with more than the smallest page size (10) get the `Pagination` bar (range, previous/next with numbered pages and ellipses, rows per page); smaller lists show none. The filter bar is always visible. While a refetch is pending the rows dim and a thin bar shows at the top of the table.
- C12. Warnings that explain themselves use an icon with a tooltip (`AtRiskFlag`), never a bare colour change. No top bar on desktop; pages carry their own title.
- C13. Tabs (`ui/tabs`) have one look and no variants: left-aligned text-only triggers on a full-width `border-b border-border` hairline, `gap-6`; the active tab is `text-foreground` with a 2px `primary` underline sitting on the hairline, inactive tabs are `text-muted-foreground`. Pages do not restyle them.
- C14. The persona picker (`/pick`, `PersonaPicker`) is a calm sign-in page in the portals' language, on the user's preset (L5): a `max-w-5xl` column (`px-6`, `py-12 sm:py-16`) with a header (the `NorthwindLogo` and "Northwind" as in the sidebar, then the `text-2xl font-semibold tracking-tight` title "Choose who you're signing in as", with no line beneath it), then three rows in this order, each a `section` with a `text-sm font-medium` heading followed by its muted `tabular-nums` count: **Clients** (one tile per client HR user, titled by the company, subtitle "<person>, HR", company initials, ordered by company name; a user without a company falls back to their name and "Client HR"), **Northwind** (the EOR's staff: the onboarding specialist, then Finance, titled by name with the role, "Onboarding specialist" or "Finance", as subtitle) and **Employees** (see below). Rows come from the database (`src/server/personas.ts`: `listPickerPersonas`, `listRecentlyStartedEmployees`); how a persona reads is `src/lib/persona-tiles.ts`; nothing is hardcoded. A group with no one shows one C7 line. Tiles sit in a `grid gap-3 sm:grid-cols-2 lg:grid-cols-3` and share one anatomy (`PersonaTile`): the whole tile is one submit button inside a `<form>` bound to the sign-in Server Action, so one click signs in and it works without JS; a `rounded-lg border border-border bg-card p-4` card, hover `bg-muted/50` with a darker border, the C2 focus ring (`focus-visible:ring-3 ring-ring/50`); left a `size-11` neutral initials avatar (`PersonaAvatar`: `bg-muted`, `font-semibold`, `rounded-lg` for a company and `rounded-full` for a person) with a small role dot (S3); right the title (`text-base font-medium`) over the subtitle (`text-sm` muted), both truncating, and an optional `text-xs` muted meta beside the title. `data-testid="persona-tile"` with `data-persona-id`. The Employees row is a button styled as the C9 search field (`h-11`, `bg-muted`, search icon, "Search N employees by name, email or company"; `data-testid="employee-search"`) that opens `EmployeeSearchDialog`, then, under a `text-xs` muted "Recently started" label, tiles for the three employees whose latest case went live most recently (name, company as subtitle, "Started Oct 5" as meta), which sign in through `pickEmployee`. The dialog is `Dialog` + an inline `Combobox`: a `h-10 bg-muted` search field on top (C9 look), then a list of every employee, one row per person with name (`font-medium`), `email · company` (`text-xs text-muted-foreground`) and the `PersonStatusBadge` (§6; omitted when the person has no case yet), the highlighted row tinted `bg-primary/10`. Typing filters on the server (name, email, company; every word must match) with a 150 ms debounce; at most 50 rows are shown and the footer then reads "Showing 50 of N. Refine your search to narrow the list."; no match shows one muted line, never an illustration. Arrow keys move the highlight, Enter signs in as the highlighted person, Escape closes, a click signs in. The dialog is anchored near the top so it does not jump as the list changes length, and uses its own padding (`p-0`, sections padded `px-6`) because the list scrolls edge to edge.
- C14a. The sidebar persona block (`PersonaSwitcher`, in `PortalShell`) shows the signed-in persona the way the picker does (avatar, title and subtitle: a client user as their company, an employee as "Employee, <company>") with a `ChevronsUpDown` icon, and opens a `Popover` above it (`w-72`, `rounded-lg border bg-popover p-1.5 shadow-md`, labelled "Switch persona") with the picker's groups: Clients and Northwind as compact rows (a `size-8` avatar, title and `text-xs` subtitle), each a one-click form calling `pickPersona` like the tiles; the current persona is a non-interactive `bg-muted/60` row with a check and `aria-current`; Employees is one "Search employees" row that closes the popover and opens the same `EmployeeSearchDialog`; a final "All personas" row under a hairline clears the session and returns to `/pick`.
- C8. Icons: lucide only, `size-4` inline with text, `size-3.5` in `sm` buttons, `text-muted-foreground` unless the icon is the action itself.
- C45. Drawers. A record opened from a list opens in the one right-hand drawer, `DrawerShell` (`src/components/drawer/drawer-shell.tsx`), never on a page of its own and never as a second drawer on top: full height on the right edge, `md` for a record, `lg` for a record with a wide table, `2xl` for a document beside a form. The header is fixed and the body scrolls under it. Header, top to bottom: an optional row with **Back** (ghost `sm`, "‹ Payment of $X", when the drawer swapped from another record) and the "N of M" stepper (chevron icon buttons named "Previous invoice" / "Next invoice", disabled at either end, hidden for a list of one) through the list it was opened from, in that list's order; the title (`text-base`) with its status badge; one muted subtitle saying what the record is ("Payroll invoice"); optional meta; then the actions. Buttons: actions live in the header only, on one row that never wraps, primary first. At most one `default` button, the record's next step labelled with it ("Pay $1,234.00"), shown only when this viewer can take it (hidden, not disabled: the drawer is a record, not a form); then `outline` secondary buttons; then utility actions (Download PDF) as `DrawerIconAction`, an `outline` icon button the height of the primary with an `aria-label` and the same words in a tooltip. Close is the dialog's corner X only (with Escape and a click outside): no Close or Cancel button and no footer. The body is one `px-6 py-6` column, `gap-6` between blocks: the facts as one compact `DrawerFacts` list (muted labels on the left), never a bordered card; subheads are `DrawerSubhead` (`text-xs font-medium` muted, an optional figure on the right); lists are flat rows with a bottom border, never nested cards or tinted bars. A status such as Overdue is said once, by the header badge. A loading body is a skeleton (`DrawerSkeleton` or one of its own shape); a failed load is `DrawerLoadError`, a destructive alert that says what is missing and that nothing changed, with an outline "Try again". It opens with `initialFocus={false}`, so no focus ring lands on the first chevron. **Staff variant** (the Finance portal's `StaffDrawer`, finance-portal §2.5): the same `PaymentPanel` and `InvoicePanel` as the client's, with slots for Finance. The subtitle or first fact names the client; header actions are Settle (primary) and outline Mark failed on a payment to settle, and Mark as paid, the Download PDF icon and the More actions menu on an invoice, each shown only when it applies; a payment's invoices and an invoice's "Payments on this invoice" swap the drawer with Back; an invoice adds a compact History (`text-sm`, the day and time muted). The one exception to "actions live in the header only": Mark failed opens an inline form at the top of the body (a bordered section with the reason, the consequence, outline Cancel and the `danger` confirm), because the reason belongs next to the record it fails; the header hides Mark failed while the form is open. A row that opens a drawer is a stretched link to the drawer's URL when it has one (`?open=<id>`, so cmd-click opens a new tab), and the list supports `j`/`k` and Enter (`DenseRow`, `RowOpener` and `useListCursor` in `src/components/dense-list.tsx`; a C6 table row uses the same `RowOpener` and `useListCursor`).
- C46. Dialog footers. A dialog with actions ends in `DialogFooter`: the `bg-muted/50` band with a top border, flush with the dialog's edges (`-mx-6 -mb-6 px-6 py-4` against the `p-6` of C10), and no button row anywhere else in the body. On `sm` and up the buttons sit right-aligned, the dismiss button first and the one primary last; below `sm` they stack with the primary on top. The dismiss button is `outline`, never `ghost`, and names what it keeps when that is clearer than "Cancel" ("Keep onboarding"). The primary is `default`, labelled with the action and its object or amount ("Pay $1,234.00", "Save role"), or the solid `danger` for a destructive confirm (C4). A state with nothing left to decide (a success) has one primary, "Done". While the action runs both buttons are disabled and the primary says what is happening ("Starting payment…"). The corner X stays. Pages do not restyle the footer.
- C47. The demo fill shortcut. Long forms that a presenter would otherwise type live register one shortcut, **Alt+Shift+D** (Option+Shift+D on a Mac; the physical D key, `DEMO_SHORTCUT_LABEL` and `isDemoShortcut` in `src/lib/demo-shortcut.ts`), with `useDemoShortcut(onFill)` (`src/components/use-demo-shortcut.ts`). It works anywhere on the page, including from inside a field, and leaves no hint in the UI: the filled form is the feedback. The screen supplies its own fill (a pure generator under `src/lib/`, taking a random source so it is testable, like `demoHire` for Start a hire): realistic values that pass the form's own validation, a different set on each press when the server would refuse a repeat (an email already on an order), never submitting for the presenter. Start a hire fills the person, work location, a role, a start date a week or two past the earliest, and the pay in the frequency the form is on, then waits on Review quote.

### 5.1 Signing and forms

Components in `src/components/signing/` and `src/components/tax-forms/` ([documents-and-signing.md](./documents-and-signing.md) §7).

- C15. Signing is always the `SigningDialog` (usually through `SignDocumentButton`): a primary "Review and sign" button opens a near-full-screen modal over the real PDF pages, and the signer clicks the highlighted tags on the document. There is no signing panel beside or under a viewer. The sticky top bar holds the title, "Required: N of M completed" with a thin progress bar, the yellow `--signing` Start button (Next once started), Finish (primary, disabled until every required field is complete), a ghost "Decline to sign" and a close icon. Decline, close, Esc and an outside click all open the same "Decline to sign?" confirmation (`variant="danger"` confirm, "Keep signing" outline). First use shows a consent card above the pages ("I agree to use electronic records and signatures" plus the one-sentence disclosure); tags stay locked until it is ticked. No drawn signatures, no signature-pad canvas.
- C16. Tags sit on the page at their `SignatureField` rectangle (percent positions, `cqw` text so they scale with the page). An unsigned signature is a `--signing` yellow flag with an arrow and "Sign here" inside a translucent yellow, `border-2` outline (initials: "Initial here"); the focused or "next" tag gets a `ring-3`. A signed tag is the typed name in the script face (F1a) on the line, dark ink (`text-signing-foreground`, never a theme foreground, because the page is white in dark mode too), with a yellow wash on hover. Date tags are read-only: a dashed yellow "Date signed" box that becomes `MM/DD/YYYY` when its signature is applied. Clicking an unsigned signature opens the nested "Adopt your signature" dialog (`sm:max-w-lg`): "Full name *" and "Initials *" in the C9 look prefilled from the signer, a bordered preview card with the script name and initials on `border-b` lines, then Cancel (outline) and "Adopt and sign" (primary, disabled until valid; a name error shows on blur, never while typing). After adoption other tags sign with one click; clicking a signed tag reopens the dialog as "Change your signature". A signed document shows `SignatureSummary` (SummaryCard rows: signer, script signature, time, document id, hash); `SignedBadge` is the one-line form (`status-success` tokens).
- C17. Form wizards (`W4Wizard`, `I9Section1Wizard`, `DirectDepositForm`, and `I9Section2Form`, which only the `/dev/forms` showcase uses; the specialist reviews Section 2 under C39 and types none of it) are one column capped at `max-w-2xl`: a text-only step list (`text-xs`, current step `font-medium text-foreground`, others muted, no numbers so they never clash with the form's own step numbers), one `FieldSet` per step with a `FieldLegend variant="label"` and a muted description, then `Continue` (default) and `Back` (outline). Errors stay hidden until the first failed Continue, then track the draft live; focus moves to the first invalid control. The last step is review: a `SummaryCard` and one primary "Review and sign" button (disabled while the document is prepared) that opens the C15 dialog over the filled PDF; there is no inline preview or signature panel.
- C18. Sensitive numbers (SSN, account number, identity-document number) use the masked field: `type="password"`, an icon button with `aria-label` "Show/Hide …" and `aria-pressed`, never autofilled. Review summaries and read-only views show `***-**-6789` / `****6789` / `•••• 6789`; the unmasked value appears only inside server-generated PDFs, and the identity-document number also in the specialist's open I-9 review (C39), where checking it against the document is the task. A Social Security card's number is an SSN and stays `***-**-6789` there too. A masked number in a read-only view carries a spoken label of its last four ("Social Security number ending in 6789").
- C19. Dates far from today (birth dates, document expirations) are typed as `MM/DD/YYYY` with the slashes inserted automatically; dates in the near future (a first day of employment) use `DatePicker`. Choices with at most four options (filing status, citizenship attestation, document list) are bordered radio cards, not dropdowns; free-text titles with common values use a `datalist`.


### 5.2 Employee pay

Components in `src/components/pay/` ([employee-pay.md](./employee-pay.md)).

- C20. The pay dashboard (`/worker/pay`) is `PageHeader` "Pay", then four tiles (Latest net pay, YTD gross, YTD taxes, Next pay date: `rounded-lg border border-border`, `text-xs` label, `text-lg font-medium tabular-nums` value, `text-xs` hint), a "Pay slips" section (L4 heading), and a read-only "Direct deposit" `SummaryCard` row after a `Separator`. The year selector is the C13 tabs, one per tax year with slips, kept in `?year=`; with one year there is no tab list (L7). The table follows C6 (no pagination: a year has at most 27 slips) and has exactly three data columns, Pay period, Gross pay and Net pay (`font-medium`), then a last column that holds one icon-only download. The pay period (`Oct 5 – Oct 18, 2026`) is the stretched link, so the whole row opens the slip. The download is an `<a download>` styled with `buttonVariants` (`ghost`, `icon`), never a `role="button"`, with a `Download` icon, `aria-label` "Download pay slip for <period>" and a `title`; it sits above the row link (`relative z-10`), so using it never opens the slip. ### 5.8 Charts

Primitives in `src/components/ui/chart.tsx` (after shadcn's `chart`, on Recharts); the Finance charts in `src/components/finance-portal/charts/` (`BilledVsCollectedChart`, `AgeingBar`, `UpcomingBillingChart`, and the hand-built `BarList` of CH10), their view models and takeaways in `src/lib/finance-chart-view.ts`. Charts are client components with plain view-model props; a server page fetches the read model (finance-portal.md §4.1) and passes it through. `/dev/charts` shows every chart (L10).

- CH1. When to chart. Use a chart when the shape is the answer: a trend over pay periods, a part of a whole, issued against expected. A single figure is a line of text in a figures line (C32, C33), a queue of things to act on is a dense list and a set of records is a table (C30); a chart never replaces any of them. A chart answers one question and does not need its legend to be read.
- CH2. Colour. Two or three hues per chart, from the chart tokens (§3.1) only, never literals and never a rainbow. `brand` is the main series; `brand-soft`, its tint, is the part of it still to come (billed but not yet collected). `positive` is for a settled series where `brand` is already taken. Status hues (`caution`, `alert`, `critical`) appear only where the data is a status, as the ageing buckets are: one red ramp (a light red, the danger foreground, a darker red) that gets heavier as things get worse, never amber or brown. Money not yet settled or not yet real (in flight, estimates) is hatched rather than a new hue: `ChartHatchPattern` in the plot, the hatched `ChartSwatch` in the legend. Colour never carries a series alone (A3): the legend names each one, and the tooltip and table repeat the figures.
- CH3. Title and takeaway. Every chart sits in `ChartFrame`: a `text-xs` muted `h3` naming the chart ("Billed vs collected") over a one-line `text-sm font-medium` takeaway that says what the reader should leave with (`variant="section"` sets the title as a `text-base font-semibold` section head with the takeaway muted beside it, unboxed, for the Finance Home) ("79% collected of $1.1M billed"). Takeaways are computed by the helper of the chart (`collectionTakeaway`, `ageingTakeaway`, `cadenceTakeaway`), never typed by a page; a page may pass its own.
- CH4. Labels. Label marks directly where there is room and nowhere else: a bar's value sits on it only when the text fits its width (`barValueLabel`), an ageing segment's only when its share clears the container-query threshold for the bar's width. Axes are quiet: no tick lines, the y axis without a line, the x axis a short period label ("Oct 5–18") or day ("Oct 16"). Every chart has a tooltip with the exact figures, and a legend under the plot (`ChartLegend`, or `ChartLegendList` with exact amounts).
- CH5. Money. Axes, bar labels and takeaways use `formatCompactCents` ("$38.5K", "$1.2M"); tooltips, legends with amounts, tables and accessible names use the exact `formatCents`.
- CH6. Accessibility. Every chart renders a visually hidden `ChartDataTable` (`sr-only`, a `caption`, `th scope`) with the same figures, so a screen reader gets the data without the plot. Recharts plots keep their accessibility layer: one tab stop on the plot (`role="application"` with an `aria-label` that carries the takeaway), the arrow keys move between periods and the tooltip card is a `role="status"` region. `AgeingBar` segments are each focusable with an accessible name stating the bucket, the exact amount and the share; with `onSegmentClick` they are buttons (`aria-pressed` for the selected one, Enter and Space), with `segmentHrefs` links (`aria-current`). The focus ring on a segment is drawn inside it, a `foreground` edge with a `background` band, so it shows on every fill. The `mini` ageing bar (8px, for table rows) is one `role="img"` whose name states the whole split.
- CH7. Empty. A chart with nothing to draw keeps its frame and takeaway and replaces the plot with `ChartEmptyState` at the plot's height (C7): one muted sentence in a dashed box. A zero bar or segment is not drawn; the legend shows zeros muted.
- CH8. Motion and size. No chart animation (`isAnimationActive={false}`; D6), so the first paint is final and reduced motion is respected without a branch. Plots fill their container (`width="100%" height="100%"` in a `ChartContainer` with a fixed height: `h-60` billed vs collected, `h-48` cadence, `h-16` the headline ageing bar), and must read at `w-80` as at full width. Widths in SVG are attributes, never inline styles (T5).
- CH9. A chart as a filter. When a chart filters the list under it, the filter lives in the URL (`?bucket=1-30` on Receivables, with the Client filter's `?client=<id>` beside it) and every mark that filters is a link, so a filtered view can be shared and cmd-click opens it in a new tab. A plain click navigates softly (`router.push` in a transition, `scroll: false`) and the list and its figures dim with a refetch bar while it loads. A link toggles only its own parameter, keeps the others and resets the page. A chart's selection combines (AND) with the page's other filters, and the chart is drawn from the data filtered by those only, so its own marks never move when one of them is clicked. The selected mark carries a `foreground` ring (and, in a bar list, a check and a bolder label); clicking it again clears it, as do its removable chip and Clear. On `AgeingBar` the other segments fade to 60% opacity at most (`DIMMED_SEGMENT_OPACITY`, never lower, so the ocean and dark fills stay readable) with their labels in `foreground` at full opacity; a bar list dims nothing. Unknown or stale values are ignored, never an error. On the Finance Home the ageing bar has no selection and its segments link to Receivables on their bucket (in flight to Payments), the top clients to Receivables on that client (C33).
- CH10. Bar list. For a ranking or a few buckets that filter something, use a hand-built bar list (`BarList`, `charts/bar-list.tsx`), not a plot: either a bordered `rounded-lg p-4` card with a `text-xs` muted title or, as on Receivables, the section variant (the Home chart's head: `text-base font-semibold` title, muted takeaway beside it, a hairline, no box), then one row per item: the label (truncating), the invoice count in `text-xs` muted, the amount right-aligned in whole dollars (`w-20 tabular-nums`, exact in `title`), and under them an `h-2` bar on a `muted` track, scaled to the longest row. Bars are status tones from the chart tokens only (CH2): ageing neutral, caution, alert, critical; a bar of several parts is drawn side by side and needs a `ChartLegendList` under the rows. Rows that filter are links with `role="button"` and `aria-pressed` (Enter and Space), named by their figures ("1 to 30 days late: $217,021.45, 36 invoices, selected"), with the focus ring of C1; a row with nothing in it is a disabled button with a muted amount. Every bar list has an `sr-only` `ChartDataTable` of its rows and `ChartEmptyState` when nothing is drawn.

## 6. Status colour

Colour carries meaning in few places: the person status, an overdue task and the at-risk flag. There is no per-step or per-state colour: onboarding progress is a stepper of stages ([tasks-and-workflow.md](./tasks-and-workflow.md) §9, C25), not a state. Five semantic status tokens let themes restyle these in one place. The client sees the three-state person status ([domain.md](./domain.md) §9.2): onboarding → `info`, active → `success`, inactive → `neutral` (`PersonStatusBadge`).

| Token | Light (`:root`) | Used for |
| --- | --- | --- |
| `neutral` | `oklch(0.97 0 0)` / fg `oklch(0.439 0 0)` | person status `inactive` |
| `info` | `oklch(0.95 0.03 250)` / fg `oklch(0.45 0.12 250)` | person status `onboarding` |
| `warning` | `oklch(0.96 0.05 85)` / fg `oklch(0.5 0.12 70)` | the at-risk flag; the "Needs you" marker on a task the client must do |
| `danger` | `oklch(0.96 0.03 25)` / fg `oklch(0.5 0.18 27)` | an overdue task's due date ("Was due Oct 20"), rejected work |
| `success` | `oklch(0.96 0.04 150)` / fg `oklch(0.45 0.12 150)` | person status `active`; completed events |

- S1. `PersonStatusBadge` is the only component that maps a `PersonStatus` to a status token. Pages pass the status; they never choose a colour.
- S2. Badge anatomy: `inline-flex items-center gap-1.5 rounded-md px-2 py-0.5 text-xs font-medium` with a `size-1.5 rounded-full` dot in the `-foreground` colour, then the human label ("Onboarding"). The at-risk flag (`AtRiskFlag`) is a warning icon after the person's name with the reason ("Pay deposit was due Oct 20.") in its accessible name and tooltip; it never replaces the status badge.
- S3. The role cue on picker and switcher avatars is a small dot (`size-2.5`, `ring-2 ring-card`) in a status token's `-foreground` colour: `client_hr` → info, `worker` → success, `onboarding_specialist` → warning, `finance` → danger. The avatar itself stays neutral (`bg-muted`); the row heading and subtitle carry the role in words (A3).
- S4. Status colour is low chroma (≤ 0.05 on backgrounds). If a status needs to shout, use weight or position, not saturation.

## 8. Accessibility

- A1. Text contrast ≥ 4.5:1 for `text-sm` and smaller; status badge foreground against its background MUST meet this (the §6 values do).
- A2. Every interactive element has a visible focus ring via `focus-visible:ring-3 focus-visible:ring-ring/50` (inherited from shadcn primitives). Never `outline-none` without a replacement ring.
- A3. Colour is never the sole carrier of state: badges always include the text label; errors always include text.
- A4. Form controls have an associated `Label`; icon-only buttons have `aria-label`.
- A5. Respect `prefers-reduced-motion`: nothing scales or slides on hover (D6); the mobile sidebar's slide uses `motion-reduce:transition-none`.

## 9. Out of scope

Free-form colour editing beyond the presets; brand colours per client company (presets only, cookie-scoped until a later slice); responsive layouts below 360 px; print styles other than the invoice document (C34); right-to-left; custom icon set; animation beyond §2 D6.
