# UI guidelines

## 1. Purpose and assumptions

This spec owns the visual language of the demo: aesthetic direction, design tokens, typography, component rules, layout, status colour, motion, and accessibility. It applies to every route in [architecture.md](./architecture.md) §5. Behaviour and access rules live in the other specs; this document only says how things look and feel.

Assumptions:

- Stack is Tailwind CSS v4 + shadcn (`base-nova` style, `neutral` base colour, CSS variables on) + lucide icons, loaded through `src/app/globals.css` and `components.json`.
- Fonts are loaded with `next/font` in `src/app/layout.tsx` (Geist, Geist Mono) and exposed as `--font-geist-sans` / `--font-geist-mono`.
- The reference aesthetic is Linear and Cursor: quiet, dense, monochrome-first, with colour reserved for meaning.

## 2. Aesthetic direction

The product should read as a serious internal tool, not a marketing site.

- D1. **Monochrome first.** Surfaces, text, and borders use the neutral scale only. Hue appears for exactly three reasons: a person status or an overdue or at-risk signal, a validation outcome, or a focused control.
- D2. **Hierarchy through weight and tone, not size.** Prefer `font-medium` + `text-foreground` versus `text-muted-foreground` over jumping type sizes. Page titles are `text-2xl`; everything else is `text-sm` or `text-base`.
- D3. **Borders over shadows.** 1px `border-border` separators and `bg-card` panels. No drop shadows except on popovers and dialogs (`shadow-md` max).
- D4. **Dense but breathable.** Default vertical rhythm is 4/8/12/16/24 px (`gap-1` … `gap-6`). Tables and lists use `py-2`–`py-3` rows. Nothing wider than `max-w-5xl` for content; forms cap at `max-w-md`.
- D5. **Restrained radius.** `--radius` is `0.625rem`; use `rounded-lg` for panels and buttons, `rounded-md` for inputs and badges, `rounded-full` only for avatars and dots.
- D6. **Quiet motion.** Transitions are 150 ms, `ease-out`, on `color`, `background-color`, `border-color`, `opacity`, `transform` only. No entrance animations on page load. Hover states shift tone by one step (`hover:bg-muted`), never scale content. The persona picker's card hover is the single allowed exception.
- D7. **No decoration.** No gradients on functional surfaces, no illustration, no emoji. The picker's radial backdrop is the only decorative element in the app.

## 3. Design tokens

All colour, radius, and font decisions flow through CSS variables defined in `src/app/globals.css` and mapped into Tailwind by the `@theme inline` block. Components reference Tailwind utilities that resolve to those variables; nothing references a palette colour directly.

### 3.1 Token families

| Family | Tokens (Tailwind utility ⇐ CSS variable) | Use |
| --- | --- | --- |
| Surface | `bg-background`, `bg-card`, `bg-popover`, `bg-muted`, `bg-secondary`, `bg-accent` | Page, panel, overlay, inset, subdued fill |
| Text | `text-foreground`, `text-muted-foreground`, `text-card-foreground`, `text-primary-foreground` | Body, secondary, text on surfaces/primary |
| Interactive | `bg-primary`, `text-primary`, `border-input`, `ring-ring` | Primary action, links, inputs, focus |
| Feedback | `text-destructive`, `bg-destructive/10` | Validation and domain errors |
| Signing (added by the signing slice) | `--signing`, `--signing-foreground` | The yellow signature tags and Start/Next button of `SigningDialog`; always dark-on-yellow because the tags sit on a white PDF page in both themes |
| Status (added by this spec, §6) | `--status-neutral`, `--status-info`, `--status-warning`, `--status-success`, `--status-danger` + `-foreground` pairs | Person status badges, overdue and at-risk signals only |
| Shape | `rounded-sm` … `rounded-xl` ⇐ `--radius` scale | Corners |
| Type | `font-sans`, `font-mono`, `font-heading` ⇐ `--font-geist-sans`, `--font-geist-mono` | §4 |

### 3.2 Rules

- T1. Components MUST use semantic token utilities (`bg-card`, `text-muted-foreground`, `border-border`). Raw palette utilities (`bg-zinc-950`, `text-sky-700`, `#hex`, `oklch(...)` in JSX) are forbidden outside `globals.css`.
- T2. New tokens are added in `globals.css` in both `:root` and `.dark`, then mapped in `@theme inline`. A token that exists in only one theme is a bug.
- T3. Theming is done by changing variable values, never by changing component classes. Presets are defined once in `src/lib/themes.ts` (`THEME_VARS`, `THEMES`) and emitted by the root layout as one `[data-theme="<id>"]` rule per preset; a preset only restyles the §3.3 variables. Status tokens are shared across presets.
- T4. Opacity modifiers on tokens (`bg-primary/80`, `ring-ring/50`) are allowed; they keep the colour tied to the token.
- T5. Pages MUST NOT define CSS. Styling lives in Tailwind utilities in JSX, `cva` variants in `src/components/ui`, and `globals.css`. No CSS modules, `<style>`, or inline `style={}` for anything a utility can express. Sole exceptions: the generated theme stylesheet in the root layout, and colour swatches whose value is data (`style={{ backgroundColor }}`).
- T6. `src/app/pick/page.tsx` renders inside `ThemeRoot force="dark"` and uses tokens only; avatar tones are the §6 status tokens.

### 3.3 Presets and application

| Preset id | Role |
| --- | --- |
| `monochrome` | Default. Near-black primary, neutral surfaces (Linear/Cursor direction) |
| `classic` | Blue primary, faint cool tint — the eor-prototype default |
| `dark` | Dark surfaces; also sets the `dark` class so `dark:` utilities apply |
| `warm`, `ocean`, `forest`, `violet` | Accent variants; faint hue tint on surfaces |

- P1. The active preset is applied server-side by `ThemeRoot` (`data-theme` on the portal wrapper), read from the `eor_theme` cookie with `monochrome` as fallback. No client-side variable injection: the first paint is already themed.
- P2. Preview (Appearance page) flips `data-theme` client-side instantly; Apply persists through a Server Action. A later slice MAY persist per client company and fall back to the cookie.
- P3. A preset defines exactly `THEME_VARS` (surfaces, text, primary, muted, accent, border, input, ring, radius). It MUST NOT redefine status tokens.

## 4. Typography

| Role | Utility | Face | Notes |
| --- | --- | --- | --- |
| Body, UI | `font-sans` | Geist | Default on `<html>` |
| Headings | `font-heading` (= sans) | Geist | Same face; weight does the work |
| Identifiers | `font-mono` | Geist Mono | Case ids, task keys (`verify_i9_section2`), state codes (`CA`), error codes |

- F1. Exactly two faces: Geist and Geist Mono. No third font.
- F2. Scale: `text-xs` (12) captions and mono literals · `text-sm` (14) default UI and table cells · `text-base` (16) long-form only · `text-lg` (18) section headings · `text-2xl` (24) page title. Nothing larger inside portals; the picker's `text-3xl/4xl` title is the exception.
- F3. Weights: `font-normal` body, `font-medium` labels/headings/buttons, `font-semibold` page title. No `font-bold`.
- F4. Numbers that align in columns (wage, markup, fee, dates) use `tabular-nums`.
- F5. Letter-spacing: `tracking-tight` on titles ≥ `text-2xl`; `uppercase tracking-[0.2em]` is reserved for the single eyebrow label ("Northwind EOR").
- F1a. Exception to F1, scoped to the typed-signature preview: Dancing Script (`assets/fonts/DancingScript.ttf`, SIL OFL) loaded with `next/font/local` in `src/components/signing/signature-font.ts`. It renders only a person's typed name as their signature (the signed tags and the "Adopt your signature" preview in `SigningDialog`, `SignatureSummary`) and matches what is stamped into the PDF. It is never used for UI text.

## 5. Components

- C1. Primitives come from shadcn into `src/components/ui/` via `pnpm dlx shadcn@latest add <name>`; they are then owned by the repo and edited in place. Allowed set for this demo: `button`, `badge`, `card`, `input`, `label`, `select`, `textarea`, `table`, `separator`, `alert`, `dialog`, `tooltip`, `skeleton`, plus `option-select`, `date-picker`, `calendar` (see C9).
- C2. Shared app components live in `src/components/`: `portal-shell`, `persona-switcher`, `persona-tile`, `employee-search-dialog`, `employee-picker`, `person-status`, `case-timeline`, `onboarding-timeline` (detailed task list), `onboarding-stages` (the stage stepper, C25), `at-risk-flag`, `document-list`, `field-error`, `empty-state`. If two portals need the same visual element, it goes here, not in both pages.
- C3. Variants are declared with `cva`, never by string-concatenating classes in pages. A page may add layout classes (`className="mt-4"`) but not restyle a primitive.
- C4. Buttons: one `variant="default"` per view (the primary action). Secondary actions are `outline`; tertiary and inline are `ghost`; destructive domain actions (reject) are `destructive` (tinted); the solid `danger` variant is reserved for the confirm step inside a dialog. Heights follow the eor-prototype: `default` is `h-10` with `px-4` (page-header actions, forms, dialogs), `sm` is `h-8` (dense toolbars only), `lg` is `h-11`. Focus rings use `focus-visible:` only.
- C5. Forms: `Label` above `Input`, `gap-1.5` between them, `gap-4` between fields. Help text is `text-xs text-muted-foreground`. Errors render in `field-error` directly under the field as `text-xs text-destructive`, using the `ActionResult.message` from [acl.md](./acl.md) §6. Submit button sits left-aligned at the bottom; no centred buttons.
- C6. Tables: header row on its own `bg-muted/60` band so it never reads as a body row, text `text-xs font-medium uppercase tracking-wide text-muted-foreground`; sortable columns use `SortableHead` (button, `aria-sort`, chevron only on the active column, none → asc → desc → none); body `text-sm`, row dividers `border-b border-border`, hover `hover:bg-muted/50`, no zebra striping.
- C7. Empty states: one line of `text-sm text-muted-foreground` plus, when a valid next action exists, one `outline` button. No illustrations.
- C9. Fields follow the eor-prototype: a filled surface (`bg-muted`), `h-10`, `rounded-lg`, a darker border on hover and `border-primary` plus a ring on focus; required labels end in ` *`. Dropdowns are `OptionSelect`: a themed select that adds a search box above 5 options (the 51-location list included), with the highlighted row tinted `bg-primary/10` and the selected row `bg-muted`. Every popup opens below the trigger without covering it, matches the trigger width, flips above when there is no room, and never leaves the viewport (`selectPopupClass` / `selectItemClass` in `ui/select.tsx` are the single source for the surface and rows). Popups portal to `<body>`, so `ThemeScope` mirrors the active theme onto it; without that they would render in the default theme. Dates use `DatePicker` over the `Calendar` primitive, styled from tokens with no vendor stylesheet (submits `YYYY-MM-DD`); the native date input is not used.
- C10. Creating a related record never leaves the workflow: it opens a dialog and returns the new record to the form (e.g. "New role" on Start a hire selects and prefills the new role). Dialogs use `p-6`; a destructive confirm uses the solid `danger` button.
- C11. Lists with more than the smallest page size (10) get the `Pagination` bar (range, previous/next with numbered pages and ellipses, rows per page); smaller lists show none. The filter bar is always visible. While a refetch is pending the rows dim and a thin bar shows at the top of the table.
- C12. Warnings that explain themselves use an icon with a tooltip (`AtRiskFlag`), never a bare colour change. No top bar on desktop; pages carry their own title.
- C13. Tabs (`ui/tabs`) have one look and no variants: left-aligned text-only triggers on a full-width `border-b border-border` hairline, `gap-6`; the active tab is `text-foreground` with a 2px `primary` underline sitting on the hairline, inactive tabs are `text-muted-foreground`. Pages do not restyle them.
- C14. The persona picker has one tile per non-employee user (Client HR, Onboarding Specialist, Finance: avatar initials, name, role; users of one role sit together in that order) plus a single **Employees** tile (`worker` tone, lucide `Users` icon, subtitle "N employees") that opens a searchable dialog instead of signing in. Both come from the database (`src/server/personas.ts`); no persona is hardcoded, and tiles wrap and centre for any count. The dialog is `Dialog` + an inline `Combobox` (`EmployeeSearchDialog`): a `h-10 bg-muted` search field on top (C9 look), then a list of every employee, one row per person with name (`font-medium`), `email · company` (`text-xs text-muted-foreground`) and the `PersonStatusBadge` (§6; omitted when the person has no case yet), the highlighted row tinted `bg-primary/10`. Typing filters on the server (name, email, company; every word must match) with a 150 ms debounce; at most 50 rows are shown and the footer then reads "Showing 50 of N. Refine your search to narrow the list."; no match shows one muted line, never an illustration. Arrow keys move the highlight, Enter signs in as the highlighted person, Escape closes, a click signs in. The dialog is anchored near the top so it does not jump as the list changes length, and uses its own padding (`p-0`, sections padded `px-6`) because the list scrolls edge to edge. The same dialog backs "Switch employee" in an employee's sidebar (`PersonaSwitcher`).
- C8. Icons: lucide only, `size-4` inline with text, `size-3.5` in `sm` buttons, `text-muted-foreground` unless the icon is the action itself.

### 5.1 Signing and forms

Components in `src/components/signing/` and `src/components/tax-forms/` ([documents-and-signing.md](./documents-and-signing.md) §7).

- C15. Signing is always the `SigningDialog` (usually through `SignDocumentButton`): a primary "Review and sign" button opens a near-full-screen modal over the real PDF pages, and the signer clicks the highlighted tags on the document. There is no signing panel beside or under a viewer. The sticky top bar holds the title, "Required: N of M completed" with a thin progress bar, the yellow `--signing` Start button (Next once started), Finish (primary, disabled until every required field is complete), a ghost "Decline to sign" and a close icon. Decline, close, Esc and an outside click all open the same "Decline to sign?" confirmation (`variant="danger"` confirm, "Keep signing" outline). First use shows a consent card above the pages ("I agree to use electronic records and signatures" plus the one-sentence disclosure); tags stay locked until it is ticked. No drawn signatures, no signature-pad canvas.
- C16. Tags sit on the page at their `SignatureField` rectangle (percent positions, `cqw` text so they scale with the page). An unsigned signature is a `--signing` yellow flag with an arrow and "Sign here" inside a translucent yellow, `border-2` outline (initials: "Initial here"); the focused or "next" tag gets a `ring-3`. A signed tag is the typed name in the script face (F1a) on the line, dark ink (`text-signing-foreground`, never a theme foreground, because the page is white in dark mode too), with a yellow wash on hover. Date tags are read-only: a dashed yellow "Date signed" box that becomes `MM/DD/YYYY` when its signature is applied. Clicking an unsigned signature opens the nested "Adopt your signature" dialog (`sm:max-w-lg`): "Full name *" and "Initials *" in the C9 look prefilled from the signer, a bordered preview card with the script name and initials on `border-b` lines, then Cancel (outline) and "Adopt and sign" (primary, disabled until valid; a name error shows on blur, never while typing). After adoption other tags sign with one click; clicking a signed tag reopens the dialog as "Change your signature". A signed document shows `SignatureSummary` (SummaryCard rows: signer, script signature, time, document id, hash); `SignedBadge` is the one-line form (`status-success` tokens).
- C17. Form wizards (`W4Wizard`, `I9Section1Wizard`, `I9Section2Form`, `DirectDepositForm`) are one column capped at `max-w-2xl`: a text-only step list (`text-xs`, current step `font-medium text-foreground`, others muted, no numbers so they never clash with the form's own step numbers), one `FieldSet` per step with a `FieldLegend variant="label"` and a muted description, then `Continue` (default) and `Back` (outline). Errors stay hidden until the first failed Continue, then track the draft live; focus moves to the first invalid control. The last step is review: a `SummaryCard` and one primary "Review and sign" button (disabled while the document is prepared) that opens the C15 dialog over the filled PDF; there is no inline preview or signature panel.
- C18. Sensitive numbers (SSN, account number) use the masked field: `type="password"`, an icon button with `aria-label` "Show/Hide …" and `aria-pressed`, never autofilled. Review summaries and read-only views show `***-**-6789` / `****6789`; the unmasked value appears only inside server-generated PDFs.
- C19. Dates far from today (birth dates, document expirations) are typed as `MM/DD/YYYY` with the slashes inserted automatically; dates in the near future (a first day of employment) use `DatePicker`. Choices with at most four options (filing status, citizenship attestation, document list) are bordered radio cards, not dropdowns; free-text titles with common values use a `datalist`.


### 5.2 Employee pay

Components in `src/components/pay/` ([employee-pay.md](./employee-pay.md)).

- C20. The pay dashboard (`/worker/pay`) is `PageHeader` "Pay", then four tiles (Latest net pay, YTD gross, YTD taxes, Next pay date: `rounded-lg border border-border`, `text-xs` label, `text-lg font-medium tabular-nums` value, `text-xs` hint), a "Pay slips" section (L4 heading), and a read-only "Direct deposit" `SummaryCard` row after a `Separator`. The year selector is the C13 tabs, one per tax year with slips, kept in `?year=`; with one year there is no tab list (L7). The table follows C6 (no pagination: a year has at most 27 slips) and has exactly three data columns, Pay period, Gross pay and Net pay (`font-medium`), then a last column that holds one icon-only download. The pay period (`Oct 5 – Oct 18, 2026`) is the stretched link, so the whole row opens the slip. The download is an `<a download>` styled with `buttonVariants` (`ghost`, `icon`), never a `role="button"`, with a `Download` icon, `aria-label` "Download pay slip for <period>" and a `title`; it sits above the row link (`relative z-10`), so using it never opens the slip. Pay date, taxes, deductions and status are not columns: they are on the slip page.
- C21. A pay slip (`/worker/pay/[payslipId]`) is a detail page in the L3 shape: a primary "Back to Pay" link, `PageHeader` "Pay slip" (period and pay date as the description, one primary "Download PDF" action), then the main column of `SummaryCard` sections (Earnings, Pre-tax deductions, Taxes withheld, After-tax deductions; empty sections are not rendered) each with a `bg-muted/60` header row ("This period", "Year to date"), one row per line (in the order the payroll domain returns them, a muted `text-xs` `detail` such as the health tier under the label), and a `strong` total row when the section has other than one line; "Taxable wages" is a muted row under the pre-tax total. The `w-80` rail holds the "Net pay" `SummaryRow` card (gross, deductions and taxes with a true minus sign U+2212, net `strong`, "Paid to") and C23. Notes from the payroll run are `text-xs` muted lines with an `Info` icon, never a coloured alert.
- C22. Pay empty states follow C7 and never show demo data: with no slip yet the section holds one `EmptyState` line, "Your first pay slip appears on your first pay date — Fri, May 22, 2026." when the next pay date is known and "Your pay slips appear here once you have been paid." otherwise; the tiles then read "—" for what does not exist (latest net pay, an unknown next pay date) and `$0.00` for year-to-date totals, and the deposit card says "No account on file". Loading is `PayDashboardSkeleton` / `PayslipDetailSkeleton`, which mirror the final layout (L2a).
- C23. "Where your money goes" is one stacked bar of the slip's gross (take-home, federal income tax, Social Security and Medicare, state taxes, health premium, 401(k), other deductions; zero segments omitted) over a legend with each amount and share. The bar is an `svg` whose widths are attributes (no inline `style`, T5), with tones from the neutral scale only (D1, T1: `primary`, then `foreground` at falling opacity), segments separated by a `stroke-card` hairline. The legend carries the meaning, so colour is never the only carrier (A3); the bar has an `aria-label` that lists the same shares.
- C24. Finance (`src/components/finance/`): invoice and payment statuses use the §6 status tokens with the S2 badge anatomy, mapped only by `InvoiceStatusBadge` and `PaymentStatusBadge`. Invoice: `open` "Due" → `neutral`, `overdue` "Overdue" → `danger`, `processing` "Processing" → `info`, `paid` "Paid" → `success`, `void` "Void" → `neutral`. Payment: `initiated` "Processing" → `info`, `settled` "Settled" → `success`, `failed` "Failed" → `danger`. Colour never carries the status alone (A3). The summary sits in one `SummaryCard`: Due now always, Overdue only when it is above zero. Each figure is a prominent value (`text-xl font-semibold tabular-nums`) with its label beneath in `text-sm` muted, and no counts or hints; Overdue takes the `danger` foreground and carries a "View" outline button that filters the invoice table. Payments in flight are not summarised there: Processing is a status. The Invoices tab lists unpaid invoices only (Due, Overdue; its filter reads All unpaid / Due / Overdue) with no service-period, pay-date or period column; the Payments tab lists every payment (paginated, C11): a payment with one invoice links its number to the invoice page in a new tab (`target="_blank" rel="noopener noreferrer"`), a payment with several shows a text `Button` "N invoices" that opens a `Dialog` titled with the payment (amount, date, status badge) listing each invoice as one whole-row new-tab link (number, person and title, period, amount); Escape closes it and focus returns to the button. The pay bar belongs to the Invoices tab only. Amounts are right-aligned `tabular-nums` (`MoneyCell`). The pay bar is a bordered `bg-card` strip pinned with `sticky bottom-4`, with no shadow (D3). The invoice drawer is a `Dialog` anchored to the right edge, with a sticky footer for Pay and Download PDF. Row and select-all checkboxes use `ui/checkbox` (added to the C1 allowed set).

### 5.3 Onboarding progress

`OnboardingStages` (`src/components/onboarding-stages.tsx`) renders the `projectStages` output for one audience ([tasks-and-workflow.md](./tasks-and-workflow.md) §8.1). It names no stage and no task: the template decides what appears.

- C25. Progress is shown as stages, never as a list of tasks. The tab opens with one headline sentence in a bordered `rounded-lg` panel (`text-sm font-medium`, a `size-4` lucide icon: `CircleAlert` in the warning token when the viewer has something to do, `Clock` muted when waiting on someone else, `CircleCheck` in the success token when all set), then one vertical stepper, the same marker-and-hairline idiom as the activity timeline. A stage is a row with a `size-4` status icon (`CircleCheck` success when complete, `CircleDot` for current, a muted `Circle` for upcoming or blocked) and its title (`text-sm font-medium`; muted when upcoming). Completed stages collapse to a single line (title, "Done", a chevron) that opens to their steps; current stages are expanded with the description, a `text-xs` summary ("4 of 6 steps done · waiting on Maya", "Due Oct 22" or "Was due Oct 20" in the danger tone, Northwind's reason in the danger tone when work was sent back) and a "View details" disclosure (native `details`, chevron rotating 90°, a focus ring) listing the other visible steps read-only as `text-xs` rows (label, owner, "Done" / "Due …" / "Not yet"); upcoming stages show only their title and a muted "Not started". After-start work is one collapsed note under the stepper. No stage ever shows internal task keys, plumbing tasks or industry jargon ("I-9 Section 2" reads "Identity & work eligibility check"): wording comes from the template's `clientLabel` / `workerLabel`.
- C26. Rows follow the viewer. The client sees a prominent row (`rounded-lg border bg-muted/30 p-3`, label `font-medium`, a warning-toned "Needs you" marker, the due date, the inline action) only for a task the client must do; everything else is stage progress text and read-only details. An employee sees a personal to-do stepper of only their own tasks in their own wording, with the same prominent row for the task they must do now. Staff see every task of every stage, hidden plumbing included. Quiet (after-start) stages are a collapsed note for the client and a normal last stage for the other audiences.

### 5.4 Task inboxes

The portal home inboxes and the generic task page ([task-inbox.md](./task-inbox.md)): `AttentionPanel`, `TaskTodoList`, `TaskInboxTable`, `TaskScreenFrame` in `src/components/tasks/`. They take view models only and name no task type.

- C27. Task status and due wording are one vocabulary everywhere a task is listed. The status badge (`TaskStatusBadge`, S2 anatomy, §6 tokens only) reads `ready` "Ready" → `neutral`, `blocked` "Waiting" → `neutral`, `done` "Done" → `success`, `rejected` "Sent back" → `danger`, `skipped` "Skipped" and `cancelled` "Cancelled" → `neutral`, and an overdue open task "Overdue" → `danger`; colour never carries the status alone (A3). Due dates use `DueLabel`: "Due Oct 22", "Due today", "Was due Oct 20" (danger foreground, `tabular-nums`) and a muted "No date" only in tables. Overdue is the only task colour in a list.
- C28. Inbox components. `AttentionPanel` (client home, above the people list) is a `rounded-lg border border-border bg-card` panel: a `border-b` header with a `size-4` `CircleAlert` in the warning token, "Needs your attention" and the count, then at most three rows (title `text-sm font-medium`; person, detail and due `text-xs` muted; the row action `outline` `sm` right-aligned) and a ghost "View all (N)" button in the header that expands the rest in place (`aria-expanded`); it renders nothing when there is nothing to do. `TaskTodoList` (employee home) is a `max-w-2xl` column: "N of M done" (`text-sm font-medium tabular-nums`) over a `h-1.5` `svg` bar (widths as attributes, T5), the next task as one `rounded-lg border bg-muted/30 p-4` card with the single primary "Continue" button, other ready tasks as quiet bordered rows with an `outline` "Open", locked tasks as muted rows with a `Lock` icon and no action, and finished work in a collapsed native `details` ("Completed (N)"). `TaskInboxTable` (specialist, Finance) is C43. Empty inboxes use C7: "You're all caught up." Loading is the matching `*Skeleton` (L2a). Staff-voice titles come from the task `title`, customers' and employees' from `clientLabel` / `workerLabel` (C25).
- C29. The task page is a detail page in the L3 shape: a primary "Back to …" link (L7), `PageHeader` with the task's title, description and status badge, the screen's own content left and a `w-80` rail right (two `SummaryCard`s: Status, Due or Completed, Waiting on, Step; then Person, Client (not for clients), Role, Start date). Screens wrap their content in `TaskScreenFrame`; a form-only screen may drop the rail. The generic fallback shows only what the task is and offers "Mark complete" or "Send back" where the registry allows it; it never invents a form. After finishing, the person lands on the next task or the inbox home with one `Alert` success line (`role="status"`, success-toned icon, the task title).

### 5.5 Finance portal

Components in `src/components/finance-portal/` ([finance-portal.md](./finance-portal.md)). They take read models and call Server Actions; they hold no billing rules.

## 6. Status colour

Colour carries meaning in few places: the person status, an overdue task and the at-risk flag. There is no per-step or per-state colour: onboarding progress is a stepper of stages ([tasks-and-workflow.md](./tasks-and-workflow.md) §9, C25), not a state. Five semantic status tokens let themes restyle these in one place. The client sees the three-state person status ([domain.md](./domain.md) §9.2): onboarding → `info`, active → `success`, inactive → `neutral` (`PersonStatusBadge`).

| Token | Light (`:root`) | Used for |
| --- | --- | --- |
| `neutral` | `oklch(0.97 0 0)` / fg `oklch(0.439 0 0)` | person status `inactive` |
| `info` | `oklch(0.95 0.03 250)` / fg `oklch(0.45 0.12 250)` | person status `onboarding` |
| `warning` | `oklch(0.96 0.05 85)` / fg `oklch(0.5 0.12 70)` | the at-risk flag; the "Needs you" marker on a task the client must do |
| `danger` | `oklch(0.96 0.03 25)` / fg `oklch(0.5 0.18 27)` | an overdue task's due date ("Was due Oct 20"), rejected work |
| `success` | `oklch(0.96 0.04 150)` / fg `oklch(0.45 0.12 150)` | person status `active`; completed events |

- S1. `PersonStatusBadge` is the only component that maps a `PersonStatus` to a status token. Pages pass the status; they never choose a colour.
- S2. Badge anatomy: `inline-flex items-center gap-1.5 rounded-md px-2 py-0.5 text-xs font-medium` with a `size-1.5 rounded-full` dot in the `-foreground` colour, then the human label ("Onboarding"). The at-risk flag (`AtRiskFlag`) is a warning icon after the person's name with the reason ("Pay deposit was due Oct 20.") in its accessible name and tooltip; it never replaces the status badge.
- S3. Role avatar tones on the picker reuse these tokens: `client_hr` → info, `worker` → success, `onboarding_specialist` → warning, `finance` → danger.
- S4. Status colour is low chroma (≤ 0.05 on backgrounds). If a status needs to shout, use weight or position, not saturation.

## 8. Accessibility

- A1. Text contrast ≥ 4.5:1 for `text-sm` and smaller; status badge foreground against its background MUST meet this (the §6 values do).
- A2. Every interactive element has a visible focus ring via `focus-visible:ring-3 focus-visible:ring-ring/50` (inherited from shadcn primitives). Never `outline-none` without a replacement ring.
- A3. Colour is never the sole carrier of state: badges always include the text label; errors always include text.
- A4. Form controls have an associated `Label`; icon-only buttons have `aria-label`.
- A5. Respect `prefers-reduced-motion`: the picker hover scale is wrapped in `motion-safe:`.

## 9. Out of scope

Free-form colour editing beyond the presets; brand colours per client company (presets only, cookie-scoped until a later slice); responsive layouts below 360 px; print styles other than the invoice document (C34); right-to-left; custom icon set; animation beyond §2 D6.
